** turn 1
*** user
symbolic linkでfile system全般に渡って同期させたいfilesがあります．これをgitでpush, pullするとsymbolic linkが切れてしまうことはないですか？　もしそうならそれを回避する方法はありますか？

*** codex
Gitはsymbolic
link自体を扱えます．ただし，Gitが保存するのはリンク先のファイル内容ではなく，*リンク先を示すパス文字列*です．したがって，=push=／=pull=だけでリンクが壊れるわけではありませんが，別環境でリンク先が存在しなければリンク切れになります．

例えば，次のような絶対パスのリンクは壊れやすいです．

#+begin_src text
project/config.yaml -> /Users/bob/shared/config.yaml
#+end_src

別PCではユーザー名や配置が異なるためです．可能ならリポジトリ内への相対リンクにします．

#+begin_src text
project/config.yaml -> ../shared/config.yaml
#+end_src

ただし，=../shared/config.yaml=がリポジトリ外なら，そのファイルはGitでは同期されません．各環境で同じ相対位置に別途配置する必要があります．

安全な方法は目的によって変わります．

- リンク先もGitで管理できる場合\\
  リンク先の実体を同じリポジトリに置き，相対symbolic
  linkを使うのが最も簡単です．

- 複数リポジトリから共通ファイルを使う場合\\
  共通ファイル専用リポジトリを作り，各環境の一定の場所へcloneします．必要ならGit
  submoduleやsubtreeも使えます．

- ホームディレクトリなど，filesystem全般へリンクを配置する場合\\
  リポジトリには実体とセットアップスクリプトを保存し，clone後にリンクを生成する方法が堅牢です．

#+begin_src sh
#!/bin/sh
repo_dir="$(cd "$(dirname "$0")" && pwd)"
ln -sfn "$repo_dir/config/app.conf" "$HOME/.config/app.conf"
#+end_src

この方式なら，各PCでスクリプトを一度実行するだけで，環境に合った絶対リンクを作れます．GNU
Stow，chezmoi，yadmなどのdotfiles管理ツールもこの用途に向いています．

注意点もあります．

- Linux／macOSでは通常，Gitはsymbolic linkをそのまま復元します．
- WindowsではDeveloper
  Modeや権限，Gitの=core.symlinks=設定によって，リンクではなく通常ファイルとしてcheckoutされる場合があります．
- リンク先がリポジトリ外なら，Gitはその内容をpushしません．
- symbolic link内に =$HOME= や =~=
  を書いても展開されません．リンク先には文字どおり保存されます．
- filesystemをまたぐsymbolic
  link自体は問題ありませんが，マウント先や外付けディスクがないとリンク切れになります．
- 機密情報をリンク先からリポジトリへ取り込まないよう注意が必要です．

結論としては，*リポジトリ内では相対リンクを使い，リポジトリ外へのリンクはセットアップスクリプトで各環境に生成する*構成が最も扱いやすいです．Gitによる同期対象はリンクではなく，リンク先の実体を置いたリポジトリにするのが基本です．

** turn 2
*** user
では，同期させたいfilesをhard linkした時はどうですか？
*** reply
hard linkは，Gitでの同期には向きません．Gitはhard
linkの関係を記録せず，各パスを独立したファイルとして管理します．

同じfilesystem上で次のように作ると，

#+begin_src sh
ln original.conf linked.conf
#+end_src

両者は同じinodeを共有するため，ローカルで一方を編集すると他方も即座に変わります．しかしGitでは，次のような問題があります．

- =clone=やcheckout後は，通常それぞれ独立したファイルになり，hard
  link関係は復元されません．
- =pull=，checkout，rebaseなどでGitがファイルを一時ファイルから置換すると，hard
  link関係が切れることがあります．
- hard linkは異なるfilesystemやボリュームをまたげません．
- ディレクトリには原則として作成できません．
- 同じinodeを指す複数のパスを追跡すると，Gitには別々のファイルとして見えます．

特に，リポジトリ内のファイルとリポジトリ外のファイルをhard
linkした場合，

#+begin_src text
repository/config.conf ──同じinode── ~/.config/app/config.conf
#+end_src

ローカル編集は反映されますが，=git pull=がリポジトリ側を新しいファイルへ置換すると，次の状態になり得ます．

#+begin_src text
repository/config.conf ── 新しいinode
~/.config/app/config.conf ── 古いinode
#+end_src

この時点で同期は止まります．明確なエラーが出ないまま関係が切れる可能性があるため，運用上かなり危険です．

したがって，おすすめは次の構成です．

#+begin_src text
Gitリポジトリ内の実体ファイル
          ↑
          │ symbolic link
          │
~/.configなどで使用する場所
#+end_src

そして，symbolic linkはclone後にセットアップスクリプトで作成します．

#+begin_src sh
#!/bin/sh
repo_dir="$(cd "$(dirname "$0")" && pwd)"

mkdir -p "$HOME/.config/app"
ln -sfn "$repo_dir/config/app.conf" \
    "$HOME/.config/app/config.conf"
#+end_src

まとめると，hard
linkは「同じマシン内で一時的に同じ内容を共有する」用途には使えますが，Gitを介して複数環境で関係を維持する用途には不適切です．Gitで管理するなら，*実体をリポジトリに置き，利用箇所からsymbolic
linkを張る方式*が最も安定します．

** turn 3
*** user
hard link先のfilesが他のgit repositoryとして管理されている場合，current directoryが属するgit repositoryからその変更を反映させるにはどうすればいいでしょう？
*** reply
hard
linkが維持されている間は，ファイル内容の変更は両方のrepositoryのworking
treeへ即座に現れます．しかし，Gitの履歴・index・commitはrepositoryごとに独立しているため，*片方でcommitしても，もう片方にはcommitされません*．

例えば，

#+begin_src text
repo-a/config.conf ── hard link ── repo-b/config.conf
#+end_src

=repo-a/config.conf=を編集すると，=repo-b/config.conf=も変更済みになります．=repo-b=へ反映するには，別途そのrepositoryでcommitします．

#+begin_src sh
git -C /path/to/repo-b status
git -C /path/to/repo-b add config.conf
git -C /path/to/repo-b commit -m "Update shared configuration"
git -C /path/to/repo-b push
#+end_src

=repo-a=側にも同じ内容を履歴として残すなら，こちらでも独立してcommitします．

#+begin_src sh
git add config.conf
git commit -m "Update shared configuration"
git push
#+end_src

つまり，ファイル内容はhard
linkによって共有されても，Git上では次のようになります．

#+begin_src text
共有されるもの：ファイル内容とinode
共有されないもの：index，commit，branch，履歴，remote
#+end_src

ただし，この構成には大きな問題があります．どちらかのrepositoryで次を実行すると，Gitによるファイル置換でhard
linkが切れる可能性があります．

#+begin_src sh
git pull
git checkout other-branch
git switch other-branch
git restore config.conf
git rebase
#+end_src

そのため，2つのrepository間でhard linkを長期維持するのは推奨しません．

より安全な構成

最も安定するのは，共有ファイルの「正本」を一方だけに決める方法です．

#+begin_src text
repo-b/config.conf       ← 正本としてGit管理
repo-a/config.conf       ← repo-bへのsymbolic link
#+end_src

=repo-a=ではsymbolic
linkだけをGit管理するか，clone後のセットアップスクリプトでリンクを作成します．

両repositoryに実体ファイルが必要なら，同期スクリプトでコピーし，それぞれcommitします．

#+begin_src sh
#!/bin/sh
set -eu

source_file="/path/to/repo-b/config.conf"
destination_file="/path/to/repo-a/config.conf"

cp "$source_file" "$destination_file"
git -C /path/to/repo-a add config.conf
git -C /path/to/repo-a diff --cached --exit-code ||
    git -C /path/to/repo-a commit -m "Sync shared configuration"
#+end_src

共有ファイル群そのものに独立した履歴が必要なら，専用repositoryを作り，各repositoryからGit
submoduleとして参照する構成も適しています．

結論として，現在のhard
linkを使い続ける場合は，変更後に対象repositoryごとに=git add=と=git commit=が必要です．ただし=pull=などでリンクが静かに切れる可能性があるため，長期運用では「正本repository＋symbolic
link」または「専用repository＋submodule」が安全です．

例えば，

#+begin_src text

#+end_src

というdirectory symbolic linkがある場合，

#+begin_src sh

#+end_src

で編集している実体は，

#+begin_src text
repo-b/shared/target_file
#+end_src

です．したがって，=repo-b=側にも変更が現れます．個々のファイルをsymbolic
linkにする必要はありません．

ただし，Git上の見え方には重要な違いがあります．

- =repo-a=は=shared=というsymbolic linkだけを管理する
- =repo-a=は=shared/target_file=を追跡しない
- =target_file=の変更は=repo-b=のworking tree上の変更になる
- =repo-b=で=git add=／=commit=する必要がある

#+begin_src sh

#+end_src

#+begin_src sh

realpath repo-a/shared/target_file
realpath repo-b/shared/target_file
#+end_src

後ろ2つが同じ実体パスを示せば，どちらの経路から編集しても同じファイルが更新されます．

#+begin_src sh

#+end_src

結論として，共有対象がdirectory全体ならdirectory単位のsymbolic
linkで問題ありません．一部のファイルだけを共有したい場合に限って，ファイル単位のsymbolic
linkを使うのが適切です．

その理解で合っています．Gitの観点では，*実体を一つのrepository内にまとめ，必要な場所からdirectoryごとsymbolic
linkする*のが自然です．=cp=で複製すると，どちらが正本か分からなくなり，差分や競合の管理が増えます．

一方，おっしゃるとおり，symbolic
linkが増えると=ls -lat=やパス構造が見づらくなります．その場合は，

- 実体を本来使うdirectoryへ置く
- そのdirectoryを所有するrepositoryでGit管理する
- 他のrepositoryからは直接参照する
- どうしても必要な場所だけsymbolic linkする

という設計がすっきりします．

要するに，Gitでは「複数箇所へ同じファイルを置く」より，「正本の場所を一つ決め，参照経路だけ用意する」と考えるのが安定します．急いで決めず，どのrepositoryがそのファイルの所有者なのかから整理すると決めやすいと思います．
